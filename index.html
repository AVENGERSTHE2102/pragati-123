01 · The big picture

Every app has two halves

What users see is only the tip. Most of the real work happens where they can't see it.

Frontend · buttons, pages, React
ServersAPIsDatabasesAuthCachingQueuesDeploy
Backend · everything that makes it work

Frontend = the dining room

Runs in the user's browser or phone. Shows data, collects clicks.

Backend = the kitchen

Runs on servers you control. Stores data, applies rules, talks to other services and AI.

Users see ~10%. The other 90% is backend — that's our focus.

01 · Backend

So what does a backend actually do?

Code that runs on a server you control — not on the user's device. Six jobs, in every app you've ever used.

Business logic

The rules: "Is the coupon valid? Can this user post?"

Store data

Users, posts, orders — safely, in databases.

Authentication

Who are you, and what are you allowed to do?

Integrations

Payments, email, maps, AI models — via their APIs.

Heavy lifting

AI, video, reports — too big for a phone.

Security

Secrets, validation, limits — enforced where users can't tamper.

Instagram, Swiggy, ChatGPT — different apps, the same six backend jobs.
Walk the six jobs as they highlight. Ask the room: which of these does Swiggy need? (All of them.)
01 · Backend

Why not do it all in the browser?

Because everything in the browser is public, editable and limited by the user's device.

view-source:app.js
// 🚨 anyone can read this
const API_KEY = "sk-live-XXXX-XXXX";
if (user.isAdmin) { … } // editable!
stolen!
User's phone memoryheavy work 💥

Must live on a server

Secret keys (payments, AI, email)
Direct database access
Rules users must not bypass
Heavy computing (AI, video)
Never trust the client. Anything in the browser can be read and changed.
Right-click → View Source: any key in frontend code is public, and any "if admin" check can be edited in DevTools. Rules and secrets must live on the server.

01 · APIs

What is an API? The restaurant analogy

An API (Application Programming Interface) is the menu + waiter: a fixed set of things you can ask for, and a safe way to ask.

You= Frontend / client
Waiter + menu= API
Kitchen= Backend + database
Food= Response (JSON)
You never walk into the kitchen. You order from the menu, and the waiter brings it back.
Follow the order ticket. The menu = the list of endpoints. You can't order what's not on the menu, and you never touch the kitchen (database) directly.

Anatomy of an HTTP request

Every API call is a small text message with the same parts. Learn these once, read any API.

Request = method + path + headers (+ body). Response = status + headers + body. JSON is just labelled data both sides understand.

01 · Backend frameworks

What backend code looks like

Different languages, same idea: when this URL is called, run this function and return JSON.

Python · FastAPI
@app.get("/posts/{post_id}")
def get_post(post_id: int):
    post = db.find_post(post_id)
    return {"id": post.id,
            "title": post.title}
JavaScript · Express
app.get("/posts/:id", async (req, res) => {
  const post = await db.findPost(req.params.id);
  res.json({ id: post.id,
             title: post.title });
});
Also popular: Django · PythonSpring Boot · JavaGin · GoNestJS · TypeScriptLaravel · PHP
Every framework follows the same pattern: route → logic → JSON response.
Show that Python and JS versions are nearly identical. Pick any framework — the concepts from this part transfer. We use FastAPI in the sprint.
01 · Architecture

Inside a backend: layers

Good backends split the work into layers, each with one job. Follow a "create post" request through them.

RouteURL → handler
Controllervalidate input
Servicebusiness logic
Repositorydata access
Databasestores it
Each layer has one job. Swap the database without touching your routes.
Names vary by framework (handlers, models, DAOs…) but the idea is the same: separate HTTP, logic, and data. This is what makes big codebases maintainable.
01 · Architecture

Monolith vs microservices

One big backend, or many small ones that talk to each other over APIs?

Monolith

Start here

Microservices

At scale
API gateway
Users

Start with a monolith. Split out a service only when it truly needs to scale on its own.
Netflix and Uber run microservices because they have thousands of engineers. A student project or startup should almost always start as a monolith.

Humans use synonyms. Keyword matching can't see that two sentences mean the same thing.

 0 shared words → nothing found

"How can I make my application faster?"

            

            
"Response-time optimization reduces latency."

            
 Same meaning → match found

          

        

        
The words differ, but the meaning is identical. We must search by meaning.

      

      
Left: keyword search flashes red on every word — no overlap. Right: semantic search connects them because they mean the same thing.

Workflow
A canvas of connected nodes = one automation.

          
Trigger node
What starts it: webhook, schedule, app event, chat.

          
Action nodes
Do one thing: send email, call an API, run code.

          
Items (JSON)
Data flows between nodes as JSON — same as APIs.

          
Expressions
Use earlier data: {{ $json.email }}

          
Credentials
API keys stored encrypted — never in the workflow.

        

        
Nodes pass JSON to each other. If you understood APIs, you already understand n8n.

      

      
Tie back to Part 01: items are JSON, HTTP Request node = calling an API, credentials = env vars done safely.

    


    

      

        04 · Triggers
        
Triggers: what starts a workflow

        
Every workflow begins with exactly one event.

      

      

        

          
Webhook
Any app calls your URL

          
Schedule
Every day at 9 AM (cron)

          
App event
New email, new row, new file

          
Chat message
Built-in chat, Telegram, WhatsApp

          
Form
Someone submits a form

        

        
A Webhook trigger is literally an API endpoint — everything from Part 01 applies.

      

      
Webhook = n8n gives you a URL; POST to it and the workflow runs. That's a backend endpoint you built without writing a server.

        04 · Choosing
        
Write code or use n8n?

        
Not a competition — they're best together.

      

      

        

          

            
Code
FastAPI · LangGraph · Express

            
 Full control over logic & performance

            
 Core product features, custom UIs

            
 Tests, version control, huge scale

            
 Slower to build every integration

          

          

            
n8n
visual workflows

            
 Working automation in minutes

            
 400+ ready-made integrations

            
 See every run's data, easy to debug

            
 Complex product logic gets messy

          

        

        
Best of both: n8n calls your backend with an HTTP Request node, and your backend triggers n8n with a webhook.

      

      
Rule of thumb: product core in code, glue & internal automations in n8n. Many startups run both.

        04 · Walkthrough
        
Build it: a Telegram AI assistant

        
Six steps from empty canvas to a bot your friends can chat with.

      

      

        

          

            
1 · Telegram Trigger
Create a bot with @BotFather, paste the token

            
2 · AI Agent
Prompt = the incoming message text

            
3 · Chat Model
Groq (fast & free tier) or OpenAI

            
4 · Memory
Keyed by chat ID, last ~10 messages

            
5 · Web search tool
HTTP Request tool → a search API (e.g. Tavily)

            
6 · Telegram: send message
Reply with the agent's output

          

          

            

              
AI Agent · system message

              
# the prompt is your "code"
You are a friendly research assistant
for college students.
- Use the web_search tool for anything
  recent or factual.
- Cite sources as links.
- Keep answers under 120 words.

            

            
Activate the workflow → it runs 24/7 on every message.

          

        

      

      
Live-demo this if time allows (~10 min). The system message is where most of the "engineering" happens.
